Notes on evaluation

My AI Agent Could See the Answer Key

I built an agentic pipeline for population pharmacokinetic model selection. It worked. Then I tried to measure how reliable it was, and found it had been reading the correct answers the entire time.

Yao Zhang

The pipeline runs four tasks end to end: fit a one-compartment model, fit a two-compartment model, compare them, and stop at a human review gate before the decision is final. Each task runs in a fresh LLM instance with no memory of the others; state moves between them through files. It picked the right structural model. The parameter estimates looked reasonable.

Here is how the leak happened, how I found it, what the clean re-run showed, and why I think it is the most useful thing I learned building this.

The setup

The pipeline analyzes a synthetic clinical trial dataset — an ADaM-format pharmacokinetic study for a fictional monoclonal antibody. Because the data were simulated, the true parameter values are known:

CL = 0.25 L/day     V1 = 3.5 L      Q  = 0.4 L/day
V2 = 2.8 L          ka = 0.3 /day   F  = 0.70

That is what makes the scenario useful. With real patient data you fit a model, get a clearance of 0.24 L/day, and have no way to know whether it is right — there is no answer key. With simulated data there is one, so you can measure not just whether the model fits, but whether it is correct.

That distinction matters more than it sounds:

Without ground truthWith ground truth
“AIC prefers the two-compartment model” “The model recovers clearance to within 3.9% of truth”
A claim about fit A claim about correctness
Circular — the model is judged by a statistic computed from its own fit External — measured against something the model never saw

So I wrote a small evaluation layer: one file holding the true values, one script scoring parameter recovery, one scoring model selection. I ran it against the completed pipeline output and got a clean table.

And then, mostly out of ordinary caution, I asked a question I had not actually asked before: which file holds the truth?

The question that found it

I knew the answer was “the ground truth file I just wrote.” But the question kept going. If the truth lives in a file, and my agent reads files, then what exactly does my agent read?

The orchestrator assembles each agent prompt from four sources:

protocol.md          universal workflow rules
study_context.md     facts about this study
progress.md          findings from completed tasks
tasks.json           the current task definition
        ↓
    the prompt the agent actually receives

I opened study_context.md. There, under a heading I had written myself:

## Ground-Truth Parameters (for post-hoc evaluation only —
## NOT visible to modeling tasks)

| TVCL | 0.25 L/day |
| TVV1 | 3.5 L      |
| TVQ  | 0.4 L/day  |
...

And higher up, in the molecule description:

- Ground truth is 2-compartment — the structural comparison task
  should still confirm this from the data rather than assume it

That file is embedded into every agent prompt. The agent was told which structural model was correct, given the exact parameter values, and then asked to determine the structural model and estimate those parameters.

The answer key was inside the exam.

Why the label did not help

The heading says “NOT visible to modeling tasks.” I wrote that myself, believing it meant something.

It is a comment in a text file. It has no enforcement. The whole file is concatenated into the prompt and handed to the model, which reads all of it. Writing “please do not look at this” on a document you hand someone is not access control.

This is obvious once stated. It was not obvious while I was writing it, because I knew what I intended the section to be, and the label described my intent accurately. The gap was between intent and mechanism.

Why it invalidates the measurement

The evaluation rests on a specific inference: the agent estimated clearance at 0.240 from the data, so the 3.9% gap from truth tells us something about how well the pipeline recovers parameters.

If the agent could read TVCL = 0.25, that inference collapses. I can no longer distinguish between:

"the data support CL ≈ 0.24"            ← what I wanted to measure
"the agent aimed near the 0.25 it saw"   ← contamination I cannot rule out

Note the shape of that second line. I am not claiming the agent did use the leaked values. I have no evidence that it did, and the fit was performed by R code running a 486-start grid search, not by a model choosing numbers it liked.

But that defense does not work, and it is worth being precise about why.

In evaluation, the possibility alone invalidates the claim.

This is the same discipline as train/test leakage in supervised learning: if a feature could encode the outcome, “the model probably ignored it” is not an acceptable answer. You do not get to argue about how contaminated a contaminated measurement was. You re-run it clean.

The part that actually worried me

Losing one set of numbers is annoying. The real problem was what came next.

The next step in this project is an ablation study — the experiment the whole thing is building toward. Three configurations:

Arm A   naive single agent, one long prompt, no task structure,
        no embedded domain rules, no verification criteria
Arm B   the structured pipeline
Arm C   Arm B plus deterministic validators

Run each several times, score every run against ground truth, and measure what the structure actually contributes.

Now consider running that experiment with the leak still in place:

Arm A (naive, sees truth)       →  probably also picks 2-compartment
Arm B (structured, sees truth)  →  picks 2-compartment
Difference: none

I would have concluded that context engineering does not matter. I would have had a clean-looking table supporting that conclusion. And the actual explanation would have been that I handed both arms the answer and measured nothing at all.

That is what separates this from the other six bugs in my engineering log. Those were things breaking — a Unicode decode error, a Windows command-line length limit, an agent reporting “complete” without persisting the state. Breakage announces itself. You get a stack trace and you go fix it.

This would not have crashed anything. It would have quietly produced a wrong conclusion that I had no particular reason to doubt.

Fixing it properly

The obvious fix is to delete the parameter table from study_context.md, which I did. I also removed the line stating the correct structural model — arguably worse than the numbers, because my headline result was “all three criteria correctly selected two-compartment,” and an agent told the answer in advance is not evidence that a pipeline can find it.

Then I verified the fix at the point that matters. Not by re-reading the file I had edited, but by generating the assembled prompt and searching that:

findstr /C:"0.25" workspace\structural_model_review\prompt.txt
findstr /C:"TVCL" workspace\structural_model_review\prompt.txt
findstr /C:"Ground truth is 2-compartment" workspace\...\prompt.txt

All three returned nothing. Checking the assembled prompt rather than the source files tests what the agent receives, not what I intended to send — the same distinction that caused the problem in the first place.

But a gap remained. The orchestrator invokes the agent with --add-dir pointed at the project root and permissions skipped, so the agent has read access to every file in the project. Moving the truth into evaluation/ground_truth.py took it out of the prompt, but not out of the filesystem.

Is the agent likely to browse into an evaluation/ folder while fitting a PK model? No. Its task rules point it at specific files, and it has no reason to wander.

But “unlikely” is not “impossible,” and I had just spent an afternoon learning that a safeguard which depends on the agent choosing not to look is not a safeguard. So I moved the entire evaluation layer outside the project directory:

C:\Projects\
├── PMX agent project\     ← the agent's --add-dir scope
└── pmx-evaluation\        ← outside it entirely

The dependency now runs one direction only: evaluation reads the project; the project cannot reach evaluation.

The difference is not cosmetic. “The answer key was outside the agent's filesystem scope” is a claim I can demonstrate. “The agent probably did not read it” is a claim I would have to defend, to someone with no reason to take my word for it.

A second leak vector

While preparing the clean re-run, I found the same mistake in a second file.

progress.md is an append-only log where each completed task records its findings, and it is fed into every subsequent prompt. That is the design — it is how state moves between agent instances that share no memory.

When I regenerated the assembled prompt after cleaning the study context and searched it again, the search lit up: the integration task's entry in the progress log carried the full ground-truth parameter table, wearing the same label — “for post-hoc evaluation only — NOT visible to modeling tasks” — while sitting inside the prompt delivered to the modeling tasks. The same mistake, in a second file, behind the same label.

It also means a re-run inherits the previous run's conclusions. Entries from the contaminated run say things like “2-compartment preferred, ΔAIC −33.81.” A fresh run reading that log does not have to reach that conclusion independently. It can just agree. So the clean re-run needed a reset progress log, not just a cleaned study context.

The generalization: leakage can enter through accumulated state, not only through static configuration. The static file was the one I thought to audit. The log that grows during execution was not — precisely because I thought of it as output rather than input, when in fact it is both.

What the clean re-run showed

With both leak paths closed — the truth removed from the study context, the progress log reset to its uncontaminated entries — I re-ran the full chain and scored it with the same evaluation scripts.

The parameter estimates came back identical to the contaminated run. Not close — identical, to four decimal places, on all six parameters:

ParameterLeaked runClean run
CL0.24020.2402
V13.51023.5102
Q0.24620.2462
V23.10733.1073
KA0.43660.4366
F_SC0.48780.4878

Model selection came back the same too: three of three criteria preferring the two-compartment model, with the same AIC, BIC, and OFV values.

So the leak, as far as I can tell, changed nothing. The estimates were determined by the data and a deterministic grid search, not by the visible answer key. The contaminated numbers turn out to have been trustworthy.

Before the re-run, “the leak probably didn't matter” was a hope. After it, it is a measurement.

Which might sound like the re-run was wasted effort. It was the opposite. The value of the clean run was never that the numbers would change — it was that whether they would change was unknowable in advance. The honest caveat: with one run per condition, this is observed reproducibility, not proof of it. The agent could have written a different fitting script the second time, and happened not to.

One thing did change: the reasoning. In the contaminated run, the review stage built its strongest counter-argument by splitting the evidence by study — showing that within the target population's own data, BIC actually favored the simpler model. In the clean run, that analysis never appeared. In its place the agent built different ones: a per-observation tally showing only 52% of observations individually improve under the selected model, a subcutaneous-bin split in which five of eight bins favor the rejected model, an information criterion recomputed at the number of subjects rather than the number of observations.

Deterministic output reproduced exactly. The model's choice of analyses did not — same skeptical posture, different arguments each time. That is a useful map of where the variance actually lives in a pipeline like this. And it answers a question the contaminated run could not: the agent's habit of arguing against its own conclusion survived the removal of the answer key, which means the skepticism was driven by the data, not by knowing where the answer was supposed to land.

The human review gate fired at the end of the clean run, as designed, and the decision was signed off with conditions binding the downstream stages.

The checklist I now use

Before trusting any benchmark result:

  1. Where does the truth live? Only in files the scoring code reads — ideally outside the tested system's filesystem scope, not merely in a different file.
  2. What does the system actually receive? Inspect the assembled input, not the source files you intended to pass.
  3. Could the answer leak indirectly? A structural hint leaks as surely as a numeric table.
  4. Is a label doing work that only code should do?
  5. Does accumulated state carry the answer forward? Logs, caches, and memory files that grow across runs are input, whatever you call them.
  6. Is n large enough to report a rate? Four of six confidence intervals covering truth, from one run, is a signal — not a coverage estimate.
  7. Does the metric measure fit or correctness? Fit statistics are internal and circular. Ground-truth error is external.

Why I think this is worth writing down

There is a lot of enthusiasm right now about building agentic systems, and comparatively little about evaluating them. The demos are impressive. The question of whether the thing is reliable tends to arrive later, if at all.

I care about this specifically because I work in a regulated field. Pharmaceutical companies are not short of people who want to use large language models. They are short of people who can demonstrate that the output is trustworthy enough to put in front of a regulator. That demonstration is an evaluation problem, and evaluation problems fail quietly.

The bug that crashes your pipeline is the cheap kind. You find it immediately and you fix it. The expensive kind lets your experiment run to completion, produce a plausible number, and support a conclusion that is wrong — with nothing in the output indicating that anything went wrong.

I found this one by asking which file held the truth. Not a sophisticated question. It just happened to be one I had not asked before.

A note on the numbers. The recovery results above were first produced in runs where the leak was present. After the fix, the full chain was re-run with the truth withheld; the estimates reproduced exactly and are reported unchanged. The ablation study the fix was necessary for is in progress.
